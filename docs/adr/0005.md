# 0005 — El borrado se bloquea cuando hay dependencias

Fecha: 2026-09-24
Estado: Aceptado

## Contexto

Casi toda entidad del sistema puede ser referenciada por otras. Una
universidad tiene carreras y profesores; una carrera tiene materias y
estudiantes; una materia tiene comisiones; una comisión tiene
inscripciones.

Qué debe pasar al eliminar un registro del que otros dependen nunca se
decidió. El comportamiento actual es simplemente el que traen las claves
foráneas: Postgres rechaza la operación, el rechazo llega a la
aplicación como una violación de integridad, y el manejador global lo
convierte en un 409.

Funciona, pero es un accidente. Nadie evaluó si es lo que se quiere, y
al no estar escrito, cada entidad nueva puede resolverlo distinto.

El ADR 0001 ya había rozado el tema al notar que borrar un profesor con
secciones asignadas queda bloqueado, pero lo dejó planteado sin
resolver.

Detrás de "eliminar un registro" conviven además dos situaciones que no
se parecen en nada. Una es corregir un error de carga: se dio de alta
una universidad con el nombre mal escrito, o dos veces. No tiene nada
colgando y no hay nada que proteger. La otra es dar de baja algo que
acumuló historia: una universidad con carreras, estudiantes,
inscripciones y notas.

## Decisión

**El borrado se bloquea cuando existen registros dependientes.**

Vale para todas las entidades del sistema, no solo para `university`.
La restricción la aplica la clave foránea, así que no hace falta código
en la aplicación para sostenerla.

**Un registro sin dependencias se elimina sin restricción.**

Es el caso de corregir un error de carga. No hay historial que
preservar, y obligar a un rodeo sería ceremonia sin propósito.

**No se cascadea.**

Cascadear significaría que eliminar una universidad arrastre sus
carreras, y con ellas las materias, las comisiones y las inscripciones,
incluidas las notas finales. Un sistema cuyo objeto es el registro
académico no puede hacer de la destrucción de historial el efecto
secundario de una operación de rutina. El riesgo es desproporcionado
frente a la comodidad que ofrece.

**No se implementa borrado lógico, por ahora.**

Marcar los registros como inactivos en lugar de eliminarlos resolvería
el caso de la institución que cierra. Pero exige una columna de estado
en cada entidad, que toda consulta del sistema recuerde filtrarla, y
responder qué ocurre con las restricciones de unicidad cuando un
registro dado de baja conserva su email. Es el camino natural si la
necesidad aparece; adoptarlo antes significa pagar ese costo en siete
entidades para un problema que todavía nadie tiene.

Se descarta relajar las claves foráneas a nulos en cascada, que dejaría
carreras sin universidad y comisiones sin profesor: filas que no
representan nada del mundo real, el mismo problema que el ADR 0001
evita al exigir profesor en cada comisión.

## Consecuencias

Quien quiera eliminar un registro con dependencias tiene que resolverlas
primero, de forma explícita. Es fricción deliberada: obliga a tomar una
decisión sobre qué pasa con lo que colgaba, en lugar de que el sistema
la tome en silencio.

El bloqueo vive en la base, no en la aplicación. Eso significa que se
sostiene venga la operación por donde venga —la API, un script de
mantenimiento, alguien conectado con `psql`— y no depende de que ningún
servicio se acuerde de verificarlo.

El mensaje actual del 409 es genérico y no dice qué dependencia bloqueó
la operación, porque el manejador usa el mismo texto para toda violación
de integridad. La decisión es correcta pero el mensaje no le sirve a
quien lo recibe. Mejorarlo implica detectar el caso antes de llegar a la
base y devolver un error que nombre el obstáculo.

Una institución que cierra no puede retirarse del sistema. Va a seguir
apareciendo en los listados indefinidamente, sin forma de marcar que ya
no está operativa. Es la limitación real que esta decisión acepta, y si
se vuelve un problema concreto la respuesta es el borrado lógico, no
debilitar esta regla.

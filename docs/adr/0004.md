# 0004 — Las restricciones de longitud viven en la base

Fecha: 2026-09-23
Estado: Aceptado

## Contexto

Tres capas pueden declarar el largo máximo de un campo de texto: la
migración de Flyway, la validación del DTO y la anotación de la entidad
JPA.

Hoy dicen cosas distintas. La migración V2 define `address` como
`varchar(300)` y `phone_number` como `varchar(30)`. El DTO valida 255 y 20. La entidad no dice nada.

El efecto práctico es que hay 45 caracteres de dirección que la base
acepta pero la API rechaza. Ese rango es inalcanzable: ningún valor
puede ocuparlo, y ningún desarrollador que lea solo una de las dos
capas puede darse cuenta de que existe.

La desalineación no fue una decisión. El DTO se escribió primero con
números elegidos a ojo, y V2 llegó después con otros, también a ojo.
Nadie cruzó los dos archivos.

La pregunta a responder no es cuál de los cuatro números es el correcto,
sino cuál de las tres capas manda.

## Decisión

**La base de datos es la restricción real.**

Es la única que nadie puede saltear, venga el dato por donde venga: la
API, un script de carga, o alguien conectado con `psql`. Una
restricción que vive solamente en la aplicación no es una restricción,
es una convención: alcanza con escribir por otro camino para violarla.

**El DTO la espeja, pero su función es otra.**

No está para proteger los datos —de eso ya se encarga la base— sino
para producir un buen error. Validar en el DTO devuelve un 400 con un
mensaje que dice qué campo falló y cuál es el límite, antes de tocar la
base. Sin esa validación, el mismo valor llega a Postgres y vuelve como
un error de integridad genérico, que el handler convierte en un 409 que
no le sirve a nadie.

La duplicación del número es deliberada: se paga repetirlo en dos
lugares a cambio de un error mucho mejor.

**La entidad no declara longitudes.**

Con Flyway y `ddl-auto=validate`, el schema nunca se genera desde las
anotaciones. Un `@Column(length = ...)` en la entidad no tendría ningún
efecto sobre la base ni sobre la validación: sería un tercer lugar para
desincronizarse, sin nada a cambio.

**Los números adoptados son 300 y 30**, los que ya tenía la base.

No son mejores que 255 y 20. Ninguno de los cuatro se eligió con
criterio. Pero 300 caracteres de dirección y 30 de teléfono son
holgados sin ser problemáticos: el estándar E.164 define un máximo de
15 dígitos para un número internacional, así que 30 sobra incluso con
prefijo y separadores.

Se descarta achicar la base a 255 y 20 con una migración V3. Achicar
una columna es una operación destructiva: falla si hay filas que no
entran, y descarta datos si se la fuerza. Pagar ese riesgo a cambio de
dos números que no son funcionalmente mejores no se justifica. Cuando
la diferencia entre dos opciones es solo estética, gana la que no
requiere migración.

## Consecuencias

Quedan dos lugares que hay que mantener sincronizados a mano, y nada lo
verifica automáticamente. El DTO puede volver a desalinearse, y el
síntoma va a aparecer tarde y lejos: un usuario que carga una dirección
larga y recibe un error que no corresponde. Es el costo directo de
aceptar la duplicación, y se asume a conciencia.

El orden de cambio queda fijado: primero la migración, después el DTO.
Al revés, la API pasa a aceptar valores que la base rechaza, y el error
sale de Postgres en lugar de la validación, que es exactamente el
escenario que esta decisión busca evitar.

La entidad queda sin `@Column(length)`. Si alguna vez se cambia
`ddl-auto` a `update` o `create`, Hibernate va a asumir 255 para todo
`String` sin longitud declarada y generar un schema distinto del real.
Es una trampa armada para quien haga ese cambio sin leer este
documento.

La política se extiende a las seis entidades que faltan. Cada vez que
una migración defina un largo, el DTO correspondiente tiene que
repetirlo con el mismo valor y mencionarlo en el mensaje de error, y la
entidad no tiene que declararlo.
